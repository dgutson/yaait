# APOSD vs Clean Code — the positions, and what yaait takes from them

> **This file is evidence, not criteria.** It records what two authors actually argued and
> what this project concluded from it. It does not set review rules. The review criteria are
> in `review.md`, whose §5 is still **PROVISIONAL** pending ROADMAP **R-001** — nothing here
> settles those questions, and the `Adopt which` column below is an input to that discussion
> rather than its outcome.

## Epistemic status — read this before using the table

Everything in the table is **argued**: two experienced practitioners disagreeing, reasoning
from career experience. Neither book's prescriptions on method length, comment density or TDD
have been measured, and both authors say so — Ousterhout concedes there is no empirical data
on TDD outcomes, Martin rests his case on practice.

`review.md` §2 is a different kind of claim: it was **counted**, across 623 million commits.
Do not let the two read as equal. Where they conflict, §2 wins, because one of them has a
denominator.

One quasi-measurement does come out of the debate, and it is worth more than the rest: the
3-4x slowdown Ousterhout measured after Martin split a single loop in two, destroying an early
exit that most candidates depended on. It is the only number either author produced by
measuring rather than recalling, and it runs against reflexive decomposition.

## Why this is not a matter of picking a side

*Clean Code* was corrective medicine for 2008, when very long functions were the common
disease. It was then read as scripture. *A Philosophy of Software Design* is the
counter-correction — and a counter-correction inherits the risk that the original disease
returns, because it argues against the excess rather than against the thing the excess was
treating.

That risk is not hypothetical. It is what `review.md` §2 measured: duplication +81%,
within-commit copy/paste +41%, cross-file reuse down 35%. The 2008 disease is returning at
machine speed. The structural diagnosis follows: **Clean Code has a floor and no ceiling;
APOSD has a ceiling and no floor.** Neither bound alone is enough.

Where both stances survive contemporary practice *and* survive the shift to generated code,
the honest answer is that this is a house-style decision belonging to the person accountable
for the codebase — not something a methodology should decide for them.
